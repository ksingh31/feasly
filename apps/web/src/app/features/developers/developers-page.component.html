Quickstart — your first estimate in 5 minutes

  1. Get a test key. Test keys start with feasly_test_ and only work against the sandbox. Contact us to have one issued for your integration.
  2. Look up an address. Autocomplete is free and needs no key: 
    curl "{{ sandboxBase }}/properties/autocomplete?q=1234+17+Ave+SW"
  3. Run an estimate. Estimates are deterministic — the same inputs always return the same figures: 
    curl -X POST "{{ sandboxBase }}/estimate" \
  -H "Authorization: Bearer feasly_test_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{{'{'}}"address": "1234 17 Ave SW, Calgary, AB",
      "livingAreaSqft": 2200,
      "finishTier": "standard"{{'}'}}'
  4. Handle the response. Success returns your estimate; failures return an RFC 7807 problem document (see Errors).

Authentication

Every request except the property autocomplete endpoint and GET /openapi.json needs an API key. Send it as a Bearer token: 

Authorization: Bearer feasly_live_YOUR_KEY
  • Live keys start with feasly_live_ and hit production.
  • Test keys start with feasly_test_ and only work in the sandbox.
  • Only the SHA-256 hash of your key is stored — the plaintext is shown once at issuance. If you lose it, rotate the key.
  • Keys carry scopes and an optional per-key rate limit (see below).

Scopes

Keys are least-privilege: each key only gets the scopes your integration needs.

ScopeGrants access to
property:readAddress autocomplete and property lookup
estimateRunning new estimates
estimate:readReading previously generated estimates
leadSubmitting leads
lead:readReading submitted leads

Default scopes for a new key: property:read, estimate, lead.

Rate limits

  • Default: 100 requests/minute per API key.
  • Exceeding the limit returns 429 Too Many Requests with a retryAfterMs hint in the RFC 7807 body — wait that long, then retry with backoff.
  • The public property autocomplete endpoint has its own IP-based limiter and needs no key.

Errors

All errors are RFC 7807 application/problem+json documents. The code field is stable and safe to switch on; message is human-readable and may change. 

{{'{'}}
  "type": "https://feasly.dev/problems/validation-error",
  "title": "Validation failed",
  "status": 422,
  "code": "VALIDATION_ERROR",
  "message": "livingAreaSqft must be at least 400",
  "retryable": false
{{'}'}}
StatusCodeMeaningRetry?

5xxINTERNAL_ERRORSomething went wrong on our sideYes — with backoff

Idempotency

Estimates are pure functions of their inputs — the deterministic cost engine returns identical figures for identical requests, so retrying an estimate is always safe. Lead submission is deduplicated on the backend: submitting the same lead twice within the deduplication window returns the original record rather than creating a duplicate.

Sandbox mode

  • Base URL: {{ sandboxBase }}
  • Use feasly_test_ keys — live keys are rejected in the sandbox and test keys are rejected in production.
  • No real emails are sent; lead submissions are recorded but never delivered.
  • Same schemas, same error codes, same rate-limit behavior as production.

API reference

The OpenAPI 3.1 spec is generated from the same Zod schemas as the code, so it can never drift. A CI drift test fails the build if the spec and the implementation disagree.

  • OpenAPI 3.1 JSON spec — {{ openapiUrl }} (public, no auth, cached 1 hour)
  • Paste the spec URL into Scalar or Redoc for an interactive reference.

Changelog & versioning

  • v1 is the current stable version. All routes live under /api/v1.
  • Deprecation policy: breaking changes ship as a new URL version (v2), never by changing v1 behavior. When v2 ships, v1 gets at least 6 months notice before removal.
  • Additive changes (new endpoints, new optional fields, new scopes) do not bump the version and are announced here.
