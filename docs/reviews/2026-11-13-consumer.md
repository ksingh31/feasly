# Feasly consumer site: design and QA review

Date: 2026-11-13. Reviewer: design + QA pass.
Evidence: 131 screenshots in `audit/shots/consumer/` and metrics in `audit/consumer-report.json`. Both come from `audit/consumer-capture.mjs` (the `audit/` folder is in this session's scratchpad).
Environment: Angular dev server at localhost:4200, running against the real dev API. The address search used live City of Calgary data, and the preview called the real `/estimates/preview`. Everything after the gate was mocked: `/leads`, `/reports/**`, narrative, revisions, shares, callbacks, magic-link and events. No real lead or email was created.
Coverage: Chromium at 1440x900 and 390x844 for every route, plus a WebKit 390x844 pass of the core flow, the renovation flow and three marketing pages.
Screenshot names follow `<slug>__<desktop|mobile>.png`. WebKit shots are prefixed `wk-`. A `-viewport.png` suffix means only the first screen was captured.

> Environment note: halfway through the first run the dev server showed a Vite overlay, `TS6053 lib.es2022.full.d.ts not found`. Something reinstalled `node_modules/typescript` at 23:57. The overlay was not product UI. The final run removes it, and the file is present again.

## Executive summary

1. **Broken for users:** the magic link from the email does not work on a new device. `/r/:token` verifies and then lands on the home page, because the report route's guard requires wizard state from localStorage. A failed estimate on the analyzing screen spins forever: the error state never renders, even after 26s and a click. Renovation users fill in four inputs and then hit a "coming soon" dead end.
2. **Honesty problems:** every total is unrounded ($3,314,460 and $3,235,979–$3,392,942), although the engine spec says to round to the nearest $1,000. The report's main figure is a single point value, with the range in small print. "Land (assessed value)" is actually the City's assessed value for the whole property, including the 1950 house. "Unlock" appears 4 times on the preview and at least 6 times across the flow; the rule is once.
3. **Funnel friction:** the path is address, scope, a details screen that repeats your choices, a preview, a five-field gate and then analyzing. That is two redundant screens. On mobile the blurred figures are below the fold on the preview, so the screen meant to motivate the gate shows only a property card and a recap.
4. **Visual and accessibility:** there is no mobile horizontal overflow anywhere (the handover issue did not reproduce). axe found 81 serious color-contrast nodes, almost all from three token problems:
   - `--muted` on `--cream-2` is 4.2:1.
   - `--accent` text on cream is 3.63:1.
   - An undefined `--brass` falls back to `#b08d3e`, which is 2.84:1.

   It also found one critical ARIA error (`aria-controls` pointing at a listbox that doesn't exist on the no-results state). There are no console or page errors on the happy path.
5. **Marketing and SEO pages are solid** (titles, meta descriptions, canonicals, noindex on private routes). The gaps: unknown URLs return HTTP 200 (soft 404), the first community guide (Beltline) opens with "we don't quote this property type", the sample report looks more polished and more honest than the real report, and print/PDF output is unbranded with no margins.

## Design findings

### Must-fix

- **M1. Round and range everything.**
  - Show the total as a range-first figure: "$3.24M – $3.39M" as the headline, with "most likely ≈ $3.31M" as secondary text. Today it is a point value with a 13px range.
  - Round to $1,000; use $10k or $0.01M at the $3M scale.
  - Round $/sq ft to whole dollars.
  - This applies to the preview, report, community figures ($609,901) and print.
- **M2. Label the land figure honestly.** "Land (assessed value)" shows $2,770,000, which is the City's total assessed value for land plus the existing 1950 house. Rename it "City-assessed property value (land + existing home), 2026". Add a one-line note: "Includes the current house; teardown value may differ." Whether this belongs in the total at all is a product decision (D-P2).
- **M3. Put the payoff in the first viewport of the preview** (`flow-04-preview__mobile-viewport.png`).
  - On 390px, the first screen is a property card and a 4-row recap; the blurred totals start around y=880.
  - Collapse the property card and recap into a one-line chip ("1412 Prospect Av SW · 2,200 sq ft · Standard · Edit").
  - Lead with the locked total card and the single CTA.
- **M4. One "Unlock".** Use it only on the preview CTA.
  - Locked notes: "Revealed when you get your free report".
  - Tier hint: "Your full report adds the cost breakdown and next steps".
  - Gate submit: "Email me my report →" / "Show my report →".
  - Landing step 3: "Get your full report".
  - Add the copy-lint test the epic specifies.
- **M5. Fix the three contrast tokens** (81 axe nodes).
  - `--muted #7a6e62` on `--cream-2`/`--accent-bg` is 4.14–4.2:1. Darken to about `#6b5f53`, or forbid muted text on cream-2.
  - `--accent #a8761a` as text on cream is 3.63:1 (eyebrows, `.code`, step numbers, the privacy link). Add `--accent-text: #8a5f12` (about 5:1) for text, and keep `--accent` for fills and rules.
  - `landing-page.component.scss:478` uses `var(--brass, #b08d3e)`. `--brass` is not a token, so it falls back to an off-palette hex at 2.84:1 on the SEO links. Use `--accent-text`.
  - `.pcard-freshness` uses `color: var(--muted); opacity: .8`, which gives 3.33:1. This is the "City-assessed value, 2026" trust line, which should be the most legible text, not the least. Remove the opacity.
  - Error page `.cta` is white on `--accent` at 3.98:1. Use the charcoal primary CTA, as elsewhere.
- **M6. Analyzing and error states must be honest and recoverable.** Fix B2. Then give every failure a specific next step:
  - Preview failure shows "We could not load your report", but there is no report yet. Say "We couldn't run your estimate".
  - Gate failure must keep the form values (it does) and say whether the lead was saved.
- **M7. Consent copy and links on the gate.**
  - "Terms and Privacy Policy" inside the consent label are plain text. Make them links that open in a new tab, so they don't lose form state.
  - Checkbox hit area is 22–24px. Make the whole label row the target, with at least a 44px row height.

### Should-fix

- **S1. Consistent primary CTA color.** New-build CTAs are charcoal (`--canvas`). Reno-scope "See My Preview", embed "Get My Estimate", error "Try again" and the community "Get a free estimate" are brass. Pick one primary style (charcoal on cream, brass on dark) and document it in `design-tokens.md`.
- **S2. Consistent content width.** Scope is about 666px, details and gate about 540px, preview and report about 680px, the reno coming-soon card about 510px. The column jumps on every step. Use one wizard column width.
- **S3. Report hierarchy** (`flow-08-report__desktop.png`). The current order is:
  - Total
  - Size stepper
  - Tier what-if, as a card nested inside a card
  - Build/Land pair, where the Land card is about 60% empty
  - Breakdown
  - How we calculate
  - AI summary
  - What it covers
  - Next steps with checkboxes
  - Planning ahead
  - Share
  - Callback
  - PDF
  - Another address

  Recommended:
  1. Header with address, date and range total.
  2. A "what makes up the total" row: Build | Land.
  3. The breakdown bar.
  4. A single "Adjust" panel combining size and tier, side by side.
  5. One "Talk to a builder" block that merges the callback, next step 1 and the builders explainer.
  6. A Share / PDF / New estimate action row.
  7. Collapsible reference sections: How we calculate, What it covers, Planning ahead, AI summary.

  Remove the "0 of 3 steps done" checkbox tracker: it has no persistence value and reads like a to-do app.
- **S4. Match the sample report to the real one, or improve the real one.** The sample is rounded, uses numbered steps instead of checkboxes and has a clean layout. Real reports should look at least as good as the sample. The sample's land figure of $165,000 is also implausible for Calgary (the guide says the community average is about $766k). Use believable numbers.
- **S5. Gate trust and placement.** The gate sub-line "Built from your City of Calgary property record — no guesswork" is italic muted text. Make it a proper trust row (City data · Fixed formula · No spam) beside the form, and show a small locked-total thumbnail so the user remembers what they're getting.
- **S6. Mobile nav.**
  - No scrim; the menu covers the H1 mid-word.
  - It lists only 3 links, so Compare and Developers are missing.
  - There is no primary "Get an estimate" action.

  Add a scrim, close on Escape and outside tap, include the CTA, and list Compare.
- **S7. Footer tap targets** (16px tall on every page). Add padding to reach a 44px row on mobile, and stack the links into a 2-column list with spacing (already partly done).
- **S8. Community guide ordering and copy** (`community-detail__*.png`).
  - `/communities` lists Beltline first. Beltline is a condo district the product can't quote, and its page leads with "We don't quote this property type yet… what the City says this property is worth". The wording says "this property" on a community page.
  - Order communities by single-family relevance or alphabetically, and fix the copy.
  - Community headline numbers use Manrope (`--font-headline`); per the tokens doc, product numbers should be `--font-ui`.
- **S9. One freshness story.** The landing page says "November 2026 — Latest data refresh". The property card says "City-assessed value, 2026 — data as of Jan 13, 2026". Users will read these as contradicting each other. Say "2026 assessment roll (City of Calgary) · checked Nov 2026".
- **S10. Off-token hex literals in consumer SCSS.** About 20 one-off values, such as `#e8e0d2`, `#fffdf8`, `#5e470c`, `#d9a441` and `#c08a24`. Fold them into tokens per the checklist in `design-tokens.md`.

### Polish

- P1. The landing "How it works" block pairs "Estimate in 2 minutes" with an unrelated sub-line ("No spam — we may reach out…"). Use the sub-line for the time and data promise instead. Time claims vary between "under 2 minutes", "about 2 minutes" and "in 2 minutes"; pick one.
- P2. The landing hero CTA "Get My Estimate" is effectively redundant: selecting a suggestion navigates immediately. Keep it for the empty state, but consider "Find my address" plus the auto-open list.
- P3. Blur radius: the totals are still partly legible as shapes ("$3,235,979" can almost be read). If the blur stays, use `blur(14px)` with a skeleton bar, or shimmer placeholders (D-P1).
- P4. The report's AI summary card repeats the deterministic-figures disclaimer inside the prose. Move the disclaimer to a caption style.
- P5. Title format is inconsistent: community pages use "Beltline Calgary Property Values… | Feasly", while every other page uses "Feasly — …".
- P6. The developers page TOC links are 18px tall, and the `<pre>` blocks aren't keyboard-scrollable (`tabindex="0"`).
- P7. The error and coming-soon pages leave a large empty band below the footer on tall screens. Use a min-height layout so the footer sits at the bottom.
- P8. "What does 'builders associated with us' mean?" appears on the gate and the report. Keep it only on the gate, next to consent.

## Flow recommendations

**Current new-build path:** landing (address) → scope → details (recap only) → preview (recap + blurred totals) → gate (5 fields) → analyzing → report. That is 6 screens before value, with the same recap shown 3 times.

**Proposed:**
1. **Landing:** pick an address and go straight to scope (keep).
2. **Scope:** the property card collapses to a chip; New build / Renovation (Coming soon) is chosen up front.
3. **Preview with gate inline:** blurred range total and build, plus an "Edit inputs" link, with the email capture directly below on the same screen. This drops `/estimate/details` and the separate `/estimate/gate` route. Keep the gate route as a deep-link target, and give it a "Back to preview" link (B5).
4. **Analyzing:** only when the real call is slow (more than 600ms). Otherwise go straight to the report. The current analyzing screen re-runs the estimate a third time (B7).
5. **Report:** structure as in S3. Partner-share and magic-link loads go through the same token-based loader (B1).

**Step indicator:** Address → Your home → Estimate. Use three honest steps that match the screens.

**Gate fields:** Email and consent are required. Name, phone and timeline should move to the report page's "Talk to a builder" block, or become optional progressive fields after unlock. Every field cut from the gate typically lifts completion.

**Renovation:** decide at the scope step (B4), with an optional waitlist email.

### Needs an owner product decision (flagged separately)

- **D-P1. Pre-gate numbers in the DOM.** The epic (03-consumer-web §4) says blurred values are never in the DOM and the API returns placeholders. The later contract comment (`packages/contracts/src/common.ts`) and the 2026-09-27 directive say the blur is a nudge, not a boundary. The docs conflict. Choose:
  - (a) Keep real digits and update the epic, or
  - (b) Render a skeleton or shimmer pre-gate and drop the figures from the preview payload.

  (b) also removes the legibility problem in P3.
- **D-P2. What "Total investment" means.** For an owner who already holds the lot, adding the full assessed property value (including the existing house) overstates the cash needed. For a buyer it is roughly the purchase basis. Options:
  - Ask "Do you already own this lot?" on scope.
  - Show Build as the headline, with "Including land at assessed value" as the secondary total.
- **D-P3. Gate field set** (email-only vs the current five) and inline vs separate-page gate.
- **D-P4. Out-of-coverage and renovation waitlists.** Capture emails for Toronto/Vancouver and for renovations (`features.renovationWaitlist` is currently false, and no UI exists).
- **D-P5. Point estimate on the report.** Is showing `base` as the big number acceptable, given the "ranges, no accuracy claims" principle? The recommendation is range-first (M1).
- **D-P6. What prints.** A branded one-page PDF summary, or print the whole web report? This decides the scope of B18.
